# Perfect Vibe Coding (PVC)

**비개발자·비전문가를 위한 Cursor AI 바이브 코딩 완벽 가이드**

이 문서는 PVC의 **제품 설명서 + 개발 교과서 + 설치·운영 가이드**입니다.  
코딩을 몰라도, “만들고 싶은 것”을 말로 설명하며 웹·앱을 만들 때 읽는 책이라고 생각하면 됩니다.

## 1. PVC가 무엇인가

### 1-1. 한 줄 정의

**PVC(Perfect Vibe Coding)** 는 Cursor 프로젝트에 **복사해 쓰는 Rules·Skills·문서 템플릿**입니다.  
AI 에이전트가 **안전하고 일관된 방식**으로 웹·앱을 만들도록 돕는 **작업 운영 레일**입니다.

“운영 체제”처럼 들리지만, 컴퓨터 OS를 설치하는 것이 아닙니다.  
**채팅으로 코딩할 때 AI가 따라야 할 규칙과, 사람이 읽을 설명서**를 미리 묶어 둔 제품킷에 가깝습니다.

### 1-2. 왜 필요한가 (바이브 코딩의 함정)

**바이브 코딩**이란, 문법보다 **원하는 결과(화면, 흐름, 문구)** 를 말로 설명하고 AI가 코드를 쓰게 하는 방식입니다.

| 장점 | 단점 (PVC 없이) |
|------|-----------------|
| 시작이 매우 빠르다 | 채팅마다 기준이 바뀐다 |
| 비전공자도 시도할 수 있다 | 중요한 데이터를 지우거나 로그인을 망가뜨릴 수 있다 |
| 아이디어를 바로 화면으로 | 페이지마다 디자인이 제각각 |
| | 유명 스킬을 통째로 깔아 비용·충돌이 커진다 |

PVC의 약속:

> **빠른 바이브 코딩은 유지**하면서,  
> **안전·일관성·문서**를 기본값으로 만든다.

### 1-3. 누구를 위한 제품인가

| 대상 | 이런 분께 맞습니다 |
|------|-------------------|
| 비개발자·비전문가 | 아이디어는 있는데 코드를 직접 쓰기 어려울 때 |
| 1인 창업자·기획자 | Cursor로 MVP·랜딩·내부 도구를 만들고 싶을 때 |
| 소규모 팀 | AI마다 결과물이 들쭉날쭉할 때 |
| 개발자 | 보안·품질·문서 기준을 저장소에 고정하고 싶을 때 |

**필수가 아닌 것:** 컴퓨터공학 학위, 프레임워크 전문가 수준.  
**있으면 좋은 것:** [Cursor](https://cursor.com/) 설치, GitHub 계정, “무엇을 만들고 싶은지”를 문장으로 말할 수 있는 능력.

### 1-4. PVC가 막아 주는 문제

| 문제 | 실제로 생기는 일 | PVC의 대응 |
|------|------------------|------------|
| 기준이 매번 바뀜 | 폴더·이름·스타일이 제각각 | 고정 규칙 + 프로젝트 사실 카드 |
| 위험한 수정 | 데이터 삭제, 로그인 사고 | 위험도 등급 + 승인 |
| 문서 없음 | “이게 뭐 하는 폴더?” | CODEMAP 습관 |
| 디자인 분열 | 버튼·색이 페이지마다 다름 | 디자인 시스템 우선 |
| 스킬 남용 | 충돌·비용·라이선스 위험 | **원칙만** 변환, 통째 설치 금지 |
| 토큰(비용) 낭비 | 매 채팅에 규칙 수백 줄 | 상시 규칙은 **2개만** |

### 1-5. 핵심 원칙 (외우지 말고, 느낌만)

1. **상시 규칙은 얇게** — 매 대화에 붙는 것은 안전 헌법 + “우리 제품 사실”만.  
2. **상황 규칙은 정확하게** — UI를 고칠 때 UI 규칙, API를 고칠 때 API·보안 규칙.  
3. **실행은 영어, 해설은 한글** — AI가 따를 짧은 명령은 영어, 사람이 읽을 설명은 한글.  
4. **유명해도 통째 설치 금지** — 필요한 원칙만 내 프로젝트에 맞게 변환.  
5. **한 주제는 한곳에** — 같은 말을 규칙·스킬·문서에 세 번 쓰지 않음.  
6. **보안·데이터가 최우선** — 예쁜 UI보다 비밀키·개인정보 안전.  
7. **기획 설문은 권장** — 필수는 아님. 비개발자는 **Quick 4문항**부터.

## 2. 처음 10분 — 빠른 시작

코딩을 몰라도 이 순서만 따르면 “PVC가 돌아가는지”를 확인할 수 있습니다.

### 2-1. 체크리스트

1. **설치 단위**를 고른다 → 처음이면 **권장 설치** ([3장](#3-설치-설명서)).  
2. (강력 권장) [`docs/pvc/개발방향-설문.md`](./docs/pvc/개발방향-설문.md) 의 **Quick 4문항**만 채운다.  
3. `.cursor/rules/project/project-context.mdc` 에 제품·금지·검사 명령을 **짧게** 채운다. (템플릿 예시는 지우고 내 말로)  
4. Cursor에서 **그 프로젝트 폴더**를 연다.  
5. Agent 채팅에 아래를 붙여 넣는다.  
6. 작은 문구 수정 한 번으로 시험한다.

### 2-2. 복붙용 — CODEMAP 초안 (코드가 없어도 됨)

```text
아직 코드가 거의 없는 새 프로젝트야. PVC 규칙을 따른다.
루트에 CODEMAP.md 초안만 만들어 줘.
최소 목차: 목적, 사용자, 스택(모름이면 빈칸), 폴더 계획, 화면 목록, 하지 말 것, 다음 할 일.
구현·파일 대량 생성은 하지 마. 초안 문서만.
```

### 2-3. 복붙용 — Quick 설문 반영

```text
개발방향 설문 Quick 답변을 반영해
project-context.mdc만 짧게 채워 줘.
코드 구현은 하지 마. 채운 내용 요약만 보여 줘.
```

### 2-4. 복붙용 — 작은 시험

```text
홈(또는 CODEMAP에 적힌 첫 화면) 제목 문구만 “환영합니다”로 바꿔 줘.
다른 파일은 건드리지 마. 위험하면 먼저 물어봐.
```

막히면 Agent에게:

```text
PVC README 「처음 10분」단계부터 한글로 차근차근 도와줘.
```

## 3. 설치 설명서

### 3-1. 준비물

| 준비물 | 설명 |
|--------|------|
| Cursor | AI와 대화하며 코드를 다루는 편집 |
| Git / GitHub | 코드를 저장·백업하는 곳 (계정만 있어도 시작 가능) |
| (선택) Node 등 | 쓸 기술은 나중에 `project-context`에 적어도 됨 |

### 3-2. 설치 단위 — 무엇을 복사할까?

PVC는 **통째로 쓰거나**, 필요한 폴더만 **골라 복사**할 수 있습니다.

| 단위 | 복사할 것 | 할 수 있는 것 | 빠지면 불편한 점 |
|------|-----------|---------------|------------------|
| **최소** | `.cursor/rules/` + `.cursor/skills/` | Agent가 규칙·스킬을 따름 | 설문·체크리스트가 내 프로젝트에 없음 → PVC 원본 저장소를 열어 참고 |
| **권장** | 최소 + `docs/pvc/` + `docs/templates/` | 설문·체크리스트·Brief를 **내 프로젝트 안**에서 작성 | 깊은 한글 해설·외부 카탈로그는 없음 |
| **전체** | 권장 + `docs/pvc-guide/ko/` + `docs/references/` | 해설·출처까지 오프라인 | — |

**추천**

- 처음·비개발자: **이 저장소 전체를 복사(fork)** 하거나 **권장 설치**.  
- 이미 앱이 있는 경우: 보통 **권장 설치**만 기존 프로젝트에 붙이기.  
- “규칙만 빨리”: **최소 설치** (설문은 GitHub PVC 페이지에서 따로 받아도 됨).

라이선스: [`LICENSE`](./LICENSE) (**MIT**) — 개인·상업적으로 복사·수정·재배포할 수 있습니다. (저작권 고지 유지)

### 3-3. 방법 A — 저장소 전체를 내 제품으로

1. GitHub에서 `perfect-vibe-coding`을 fork 하거나 ZIP/클론으로 받는다.  
2. 폴더·저장소 이름을 내 제품명으로 바꾼다.  
3. Cursor → Open Folder → 그 폴더.  
4. [2장 10분 시작](#2-처음-10분--빠른-시작)으로 진행.

### 3-4. 방법 B — 이미 있는 앱에 PVC만 붙이기

1. 이 저장소에서 **권장 설치**에 해당하는 폴더를 내 앱 **루트**에 복사한다.  
2. `project-context.mdc`를 내 제품 내용으로 채운다.  
3. Cursor에서 앱 폴더를 연다.  
4. “이 프로젝트는 PVC(.cursor/rules)를 따른다”고 Agent에게 한 번 말해 두면 좋다.

### 3-5. 설치 후 확인

- Cursor Settings / Rules 에 프로젝트 규칙이 보이는지  
- Agent에게 `CODEMAP 초안만` 요청이 되는지  
- [`docs/pvc/CHECKLISTS.md`](./docs/pvc/CHECKLISTS.md) A절을 체크

## 4. 기획 설문 (권장)

### 4-1. 왜 설문이 있나?

AI는 **추측**을 잘합니다. 추측이 쌓이면 나중에 고치기 어렵습니다.  
설문은 **당신 머릿속 기획을 글로 꺼내** Agent가 정확히 이해하게 돕는 도구입니다.

- **필수 아님** — 없어도 PVC는 동작합니다.  
- **별도 파일** — 다운로드·복사해서 다른 프로젝트에 재사용해도 됩니다.  
- 파일이 길어도, **Quick만** 쓰면 됩니다.

파일: [`docs/pvc/개발방향-설문.md`](./docs/pvc/개발방향-설문.md)

### 4-2. 등급 — 얼마나 채울까?

| 모드 | 이런 때 | 얼마나 쓰나 |
|------|---------|-------------|
| **Quick** | 실험, 랜딩, 단일 화면, “일단 보여주기” | **4문항만** ← 비개발자 기본 |
| **Standard** | MVP, 실제 손님·직원이 쓸 서비스 | 설문 본문 전체 |
| **High Risk** | 로그인, 결제, 개인정보, DB, 배포, 대규모 개편 | 전체 + Feature Brief + 작업 전 승인 |

### 4-3. Quick 4문항 (여기서 시작)

설문 파일 상단에 표가 있습니다. 요약하면:

1. 무엇을 만드나요? (한 문장)  
2. 누가 쓰나요?  
3. 형태는? (웹 / 모바일웹 / 앱 / 랜딩 / 관리자 …)  
4. 이번에 하지 말 것·절대 금지 (없으면 `없음`)

모르는 칸은 `모름` / `추천 부탁` 이라고 적어도 됩니다.

### 4-4. 설문 → Agent로 넘기는 말

```text
docs/pvc/개발방향-설문.md (또는 내 답변 파일)을 읽고
project-context.mdc와 CODEMAP 초안에만 반영해 줘.
코드 구현은 내가 승인한 뒤에만 해.
```

## 5. 프로젝트 사실 카드

### 5-1. 설문과 사실 카드의 차이

| | 설문 (`개발방향-설문.md`) | 사실 카드 (`project-context.mdc`) |
|--|---------------------------|-------------------------------------|
| 길이 | 길어도 됨 (기획용) | **짧아야 함** (매 채팅에 붙음) |
| 필수? | 권장 | **거의 필수에 가깝게 권장** (비우면 AI가 추측) |
| 역할 | 생각을 정리 | Agent의 “우리 제품 메모” |

### 5-2. 어디에 있나?

`.cursor/rules/project/project-context.mdc`

### 5-3. 최소한 채울 것

| 항목 | 예시 (그대로 쓰지 말고 내 것으로) |
|------|-----------------------------------|
| 제품 한 줄 | “동네 카페 예약 웹앱” |
| 누가 쓰나 | “사장님 + 손님, 스마트폰 많음” |
| 기술 스택 | 쓰는 것만. **모름이면 `모름·추천 부탁`** |
| 하면 안 되는 것 | “운영 고객 데이터 삭제 금지” |
| 완료 전 검사 | 있으면 lint/test/build 명령. 없으면 나중에 |

템플릿에 적힌 Next.js, Prisma 등은 **예시**입니다.  
“PVC = Next 전용”이 아닙니다. 안 쓰면 **지우고** 채우세요.

### 5-4. 사실 카드가 길면?

다시 길어지면 토큰(비용)이 늘어납니다.  
자세한 사연·기획은 설문·CODEMAP·DESIGN에 두고, 사실 카드에는 **매 작업마다 필요한 사실만** 남기세요.

## 6. 폴더와 파일 — 한눈에 보는 지도

```text
perfect-vibe-coding/          (또는 내 프로젝트)
│
├── README.md                 ← 지금 읽는 완벽 가이드 (사람용, 한글)
├── LICENSE                   ← MIT 라이선스
├── RULES_MAP.md              ← 규칙 지도 (어떤 파일이 언제 쓰이나)
│
├── .cursor/
│   ├── rules/                ← AI가 따르는 실행 규정 (영어)
│   │   ├── core/             ← 헌법, 안전, 스킬 도입 기준 …
│   │   ├── project/          ← 사실 카드 (우리 제품)
│   │   ├── architecture/ security/ design/ …
│   │   └── manual/           ← 마이그레이션·장애 등 (위험할 때만)
│   └── skills/               ← 상황별 작업 절차 (영어)
│       ├── skill-router/     ← “이번 일엔 뭘 쓰지?”
│       └── external-skill-import/  ← 외부 스킬 안전하게 가져오기
│
└── docs/
    ├── pvc/
    │   ├── 개발방향-설문.md  ← 기획 초안 (권장, 별도 사용 가능)
    │   ├── 개발방향-설문-폼.html ← 브라우저 작성 → MD/JSON 내려받기
    │   ├── CHECKLISTS.md     ← 설치·시험·회고
    │   └── DECISIONS.md      ← 중요한 결정 기록
    ├── templates/            ← Brief / Blueprint 양식
    ├── pvc-guide/ko/         ← 한글 상세 해설 (자동으로 AI에 안 붙음)
    └── references/           ← 외부 출처 카탈로그
```

**기억할 것:**  
사람이 읽는 긴 한글 설명은 `docs/`에 두고,  
AI가 매 채팅에 자동으로 들이마시는 것은 `.cursor/rules` 중 **아주 일부**뿐입니다.

## 7. Agent에게 말하는 법 (교과서)

### 7-1. 좋은 요청의 공통점

- **범위가 보인다** (어디를, 얼마나)  
- **하지 말 것이 보인다**  
- **성공 모습이 보인다** (어떤 화면·결과)

### 7-2. 좋은 예

```text
로그인 없이 보이는 랜딩 첫 화면에
제품명과 CTA 버튼 하나만 넣어 줘.
다른 페이지는 건드리지 마.
```

```text
예약 목록은 서버에서만 DB를 보게 하고,
화면에서는 목록을 받아 보여 주기만 해.
```

```text
이 버튼 색만 브랜드 토큰에 맞게.
레이아웃은 바꾸지 마.
```

### 7-3. 피하면 좋은 예

| 말 | 왜 위험한가 |
|----|-------------|
| “전체적으로 예쁘게 리팩터해 줘” | 범위가 무한 → 코드가 한꺼번에 바뀜 |
| “유명한 스킬 전부 설치해” | 충돌·비용·라이선스 |
| “일단 운영 DB에 연결해서 테스트해” | 실제 고객 데이터 사고 |
| “알아서 최신 트렌드로” | 기준이 없어 매번 달라짐 |

### 7-4. 큰 기능을 맡길 때

```text
skill-router 기준으로 이번 작업에 필요한 규칙·스킬만 골라 줘.
변경 계획 짧게 보여 준 뒤, 내가 승인한 뒤에만 코드를 수정해.
```

### 7-5. 역할 나누기 (당신 vs Agent)

| 당신이 할 일 | Agent가 할 일 |
|--------------|----------------|
| 무엇을·누구를·하지 말 것 | 코드·파일 수정 |
| 승인 (위험할 때) | 짧은 계획·위험 고지 |
| 화면을 눈으로 확인 | 시킨 검사만 실행·보고 |
| 설문·사실 카드 채우기 | CODEMAP 등 문서 초안 |

## 8. 위험도 — 언제 멈추고 승인하나

정본은 `.cursor/rules/core/00-development-governance.mdc` 에 있습니다.  
README는 **쉬운 요약**만 합니다.

| 등급 | 쉬운 예 | Agent가 해야 할 일 |
|------|---------|-------------------|
| **Low** | 문구, 색, 버튼 하나 | 바로 수정 후 가볍게 확인 |
| **Medium** | 새 화면, 폼, API 기능 추가 | **짧은 계획**을 보여 준 뒤 수정 |
| **High** | 로그인, 결제, 개인정보, DB 구조, 배포, 라이브러리 대량 추가 | **당신이 “해”라고 하기 전엔 구현 금지** |
| **Critical** | 운영 데이터 삭제, 비밀키 교체, 서버 인프라 삭제 | 단계·백업·롤백 계획 + 승인 필수 |

비개발자가 “정리해 줘”라고만 해도 AI가 폴더를 크게 옮기거나 파일을 지울 수 있습니다.  
그럴 때는 **High**로 보고 승인을 요구하는 것이 PVC의 안전벨트입니다.

## 9. 규칙·스킬이 “켜지는” 방식

### 9-1. 스위치 비유

PVC 규칙을 전등 스위치라고 생각하세요.

| 스위치 | 의미 | 쉬운 말 |
|--------|------|---------|
| **Always** (항상) | 매 채팅 | 안전 헌법 + 우리 제품 사실 (**2개만**) |
| **Globs** | 관련 파일을 열·고칠 때 | UI 파일 → 디자인 규칙, API 파일 → 보안·데이터 규칙 |
| **Agent / Skill** | 작업 성격에 맞게 | “스킬 라우터야, 이번엔 뭐 쓰지?” |
| **Manual** | 드물고 위험할 때 | DB 이사, 장애 대응 — 일부러 부를 때만 |

그래서 **버튼 글자만 바꾸는데 DB 규칙이 잔뜩 붙지 않게** 설계되어 있습니다.

### 9-2. 역할 분리 (한 주제 한곳)

| 종류 | 역할 | 넣지 말 것 |
|------|------|------------|
| Rules | “반드시 이렇게” 짧은 명령 | 긴 절차, 빈칸 양식 |
| Skills | “이 작업은 이 순서로” | 헌법을 다시 장황하게 쓰기 |
| Docs (한글) | 왜 / 예시 / 배경 | AI가 매 채팅에 자동 로드한다고 가정 |
| Templates | 복사해서 채우는 양식 | 정책의 원본 |
| References | 출처·후보 목록 | “이 저장소 통째 설치” |
| 설문 | 기획 초안 (권장) | Always 규칙 대신 쓰기 |

자세한 지도: [`RULES_MAP.md`](./RULES_MAP.md)

### 9-3. 영어 규칙 vs 한글 해설

- AI가 실제로 따르는 실행 규칙은 **영어** `.mdc` / `SKILL.md`  
- 당신이 이해하는 긴 설명은 **한글** (`README`, 설문, `docs/pvc-guide/ko/`)  
- 한글 해설은 **보조 문서**입니다. 내용이 달라 보이면 **영어 실행 규칙**을 기준으로 하고, 오류면 Issue/PR로 고칩니다.

### 9-4. 동작이 잘 되는지 시험하려면

[`docs/pvc/CHECKLISTS.md`](./docs/pvc/CHECKLISTS.md) 의 **스모크 7시나리오**를 따라 한 번씩 요청해 보세요.  
예: “버튼 문구만”, “관리자만 보는 화면”, “테이블 컬럼 삭제” 등 — 기대 행동이 표로 적혀 있습니다.

- **부족하거나, 더 나은 판단·코딩에 도움이 되는 원칙만** 프로젝트에 맞게 변환합니다.

## 11. 자주 묻는 질문 (FAQ)

**Q. 설문을 꼭 써야 하나요?**  
A. 아니요. **권장**입니다. 비개발자는 **Quick 4문항**만으로도 효과가 큽니다.

**Q. `.cursor` 폴더만 복사해도 되나요?**  
A. 됩니다(**최소 설치**). 설문·체크리스트는 PVC GitHub를 열어 보거나 **권장 설치**를 쓰세요.

**Q. Next.js를 안 쓰는데요?**  
A. 괜찮습니다. `project-context`의 예시 스택을 지우고 바꾸면 됩니다. PVC는 특정 프레임워크 전용이 아닙니다.

**Q. 영어 규칙 파일을 내가 다 읽어야 하나요?**  
A. 아니요. 이 README·설문·`docs/pvc-guide/ko/`가 사람용입니다.

**Q. 한글 설명과 영어 규칙이 다르면?**  
A. **영어 실행 규칙**을 따르고, 차이를 발견하면 수정(Issue/PR)하세요.

**Q. 스킬을 잔뜩 설치하면 더 똑똑해지나요?**  
A. 보통 **아닙니다**. 충돌·비용·라이선스 위험이 커집니다. 원칙만 가져오세요.

**Q. Agent가 자꾸 멈춰서 물어보면?**  
A. High/Critical(로그인·결제·DB 등)일 수 있습니다. 범위를 좁히거나, 이해한 뒤 **명시적으로 승인**하세요.

**Q. Agent가 승인 없이 큰 변경을 하면?**  
A. 채팅에서 롤백·되돌리기를 요청하고, `core/00` 위험도를 다시 상기시키세요.  
`위험도 High면 승인 전에 구현하지 마` 라고 명시해도 좋습니다.

**Q. 이미 만든 프로젝트에 나중에 PVC를 붙여도 되나요?**  
A. 됩니다. 권장 설치 복사 → `project-context` 채우기 → 작은 수정부터. 한 번에 전체를 리팩터하지 마세요.

**Q. 토큰(비용)이 걱정돼요.**  
A. PVC는 그래서 Always를 2개로 줄였습니다. 설문을 Always에 넣지 말고, 한글 장문을 rules에 복사하지 마세요.

## 13. 상황별 완성 로드맵

### 13-1. 주말에 랜딩 페이지만

1. 권장(또는 전체) 설치  
2. 설문 **Quick**  
3. project-context  
4. CODEMAP 초안  
5. “히어로에 제품명+CTA”부터  
6. CHECKLISTS 스모크 1번(문구 수정) 시험  

### 13-2. 손님이 쓰는 MVP

1. 설문 **Standard**  
2. project-context + CODEMAP + (가능하면) DESIGN 초안  
3. 기능은 하나씩, Medium은 계획 후  
4. 로그인·결제가 나오면 **High** — 승인 필수  
5. 끝날 때 CHECKLISTS 회고  

### 13-3. 이미 코드가 있는 서비스에 PVC만

1. 권장 설치만 복사  
2. Quick 또는 Standard로 “하지 말 것”을 분명히  
3. project-context에 실제 스택·금지 기입  
4. 작은 수정부터 — 전면 리팩터 금지

## 마치며

PVC는 “완벽한 규칙 더미”가 아닙니다.

> **지금 하는 일과 위험도에 맞는 최소 레일만 정확히 주고,  
> 좋은 외부 자료는 원칙만 골라 쓰며,  
> 비개발자도 말로 제품을 만들되 데이터가 안전하고 결과물이 일관되게 쌓이게 하는 것.**

오늘 할 일 한 줄:

**권장 설치 → Quick 설문 → 사실 카드 → CODEMAP 초안 → 작은 수정 하나.**

그다음부터는 이 가이드의 해당 장만 펼치면 됩니다.
